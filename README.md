# Параллельный поиск максимума

Учебный проект модуля «Основные пакеты Go» по шаблону
[Yandex-Practicum/go1fl-sprint9-final-tpl](https://github.com/Yandex-Practicum/go1fl-sprint9-final-tpl).

Требуется Go 1.24.1 или новее, внешние зависимости отсутствуют.

```sh
go run .
```

Программа генерирует `SIZE = 100_000_000` положительных целых чисел, находит
максимум последовательно и с помощью `CHUNKS = 8` горутин. Длительности обоих
поисков выводятся в микросекундах. На 64-битной платформе один массив занимает
около 800 МБ памяти: для полного запуска требуется соответствующий запас ОЗУ
или swap. Генерация массива не входит в измеряемое время поиска.

## Алгоритм

`maximum` выполняет линейный проход. Для пустого или nil-слайса возвращает 0.
Начальное значение берётся из первого элемента, поэтому поддерживаются и
отрицательные числа.

`maxChunks` распределяет остаток от деления между первыми частями. Все элементы,
включая хвост массива, обрабатываются ровно один раз. Каждая из восьми горутин
записывает результат в отдельную ячейку; `sync.WaitGroup` синхронизирует чтение
результатов. При количестве элементов меньше восьми пустые части не участвуют
в заключительном поиске. Входной слайс не изменяется.

Суммарная вычислительная сложность обоих способов — O(n). Параллельный способ
использует восемь дополнительных результатов. Ускорение зависит от процессора,
пропускной способности памяти, размера данных и загрузки системы; на малых
массивах затраты на горутины могут сделать его медленнее.

## Проверки

```sh
go test -race -count=1 -cover ./...
go vet ./...
go test -fuzz=FuzzMaximumsAgree -fuzztime=5s -parallel=2
```

Тесты покрывают пустой, nil, единичный, короткий и некратный восьми слайс,
отрицательные значения, крайние значения int, максимум в каждой позиции,
неизменность входных данных и сравнение с независимой реализацией `slices.Max`.
Для отрицательного и нулевого размера генератор возвращает пустой слайс.

Полный запуск на 100 миллионах элементов выполнен в РЕД ОС 8 (Linux arm64),
Go 1.24.1. Оба алгоритма вернули одинаковый максимум. В сохранённом запуске
последовательный поиск занял 272094 мкс, параллельный — 55819 мкс. Это один
замер, а не гарантия ускорения. Вывод программы, тестов и фаззинга — в `evidence/`.
